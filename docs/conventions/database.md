# 数据库建模与完整性

> 层：规范 · 时态：约束未来 · 失效：数据库选型或建模决定变更时

## 目的

约束表结构与数据库自身保证；访问、事务和迁移见 persistence.md，权限见 authorization.md。

## 何时读取

新增或修改 Prisma model、字段、关系、数据库约束和索引时。

## 适用范围

PostgreSQL schema 与受版本管理的迁移；新增/修改的模型执行新结构检查。源码声明不能代替线上数据库证据。

## 表职责与命名

1. 每个模型必须说明所属业务域、实体/配置/关联/投影/历史事实职责、维护方和保留策略；声明格式见第 5 项，具体业务决定进对应 PRD。
2. model 必须 PascalCase 单数，字段 camelCase；物理表通过 @@map 使用蛇形复数，物理列保持 camelCase；禁止技术前缀、产品前缀、模块名前缀与歧义缩写；领域前缀仅按第 5 项登记表使用。 `PER-4.1`
3. 必须定义主键或联合主键；主键与业务唯一键分开设计，生成方、存储类型和外部表示必须明确。新增或修改模型必须有职责说明、显式主键及表名映射。 `DB-4.1`
4. User、Role 等跨域词义沿用现有决定；其他领域同义实体必须加业务限定词，禁止擅自复用。
5. 新增或修改的 model 首行必须单独一行 `// 域: <上下文>`，上下文必须在下方登记表内；所有上下文前缀非空，`@@map` 必须使用登记前缀，不再登记「无前缀」上下文。新增上下文须先登记并附 ADR。 `DB-4.2`

## 字段语义

1. 业务事实模型必须有 createdAt/updatedAt；关联表、同步投影和只追加事实按职责决定，禁止机械添加版本、软删或审计字段。
2. 每个自行声明的持久化字段必须有自包含说明，明确非显然单位、默认值、null 含义和敏感性；Prisma 的 /// 说明不等于数据库 COMMENT，SQL 注释随迁移维护范围由评审确定。
3. 字符串必须明确业务长度、大小写和空白规范；数值必须明确范围和单位；默认值必须是真实默认行为。
4. 金额与价格必须明确 Decimal 或最小单位、精度、舍入和溢出规则，覆盖存储、计算、API；禁止未经边界证明转换为浮点计算。
5. 必须区分业务日期与时间点，明确 UTC、时区和精度；ORM 的 @updatedAt 和 uuid() 不等于数据库触发器或原生 UUID 列。
6. JSON 必须有结构校验；核心关联或频繁检索字段应该独立建模；封闭枚举必须用 Prisma enum。

## 唯一、引用与删除

1. 业务唯一性必须由数据库约束兜底，明确作用范围、大小写、null 和软删行为；禁止只依赖先查后写。
2. 新增或修改模型中的持有外键字段的关系必须显式声明 onDelete；Restrict/Cascade/SetNull 必须符合数据归属和保留要求。机器只检查声明存在，不替代策略评审。 `DB-5.1`
3. 纯关联表必须通过联合主键或唯一约束防重复；历史事实不得因便利而级联删除。
4. 非负数、范围、起止关系等必须评估 CHECK；Prisma 可表达约束放 schema，无法表达部分用迁移 SQL 维护并验证保留。
5. 软删除默认不采用；引入必须有 ADR，统一 deletedAt，并评审唯一性、查询、关系和清理。

## 索引

1. 每个新增索引必须关联实际过滤、排序、关联或分页查询，说明字段顺序；禁止机械为每个字段建索引。
2. 外键引用方索引必须评估，不能假设 PostgreSQL 自动创建；禁止重复声明完全相同的普通索引。 `DB-6.1`
3. 频繁查询必须使用代表性数据与执行计划验证；低基数字段、部分索引和表达式索引按实测决定。

## 结构变更与迁移

1. 数据库结构差异必须对应新增迁移；是否产生 DDL 必须由离线 migrate diff 判断，禁止要求纯注释或 ORM 变化机械新增空迁移。 `DB-7.1`

## 验证方式

- scripts/checks/database.ts 检查修改模型的主键、映射、职责说明、域声明、表名前缀、显式删除策略与重复普通索引；scripts/checks/rules.ts 校验上下文登记表自身；语法由 prisma validate 承接。复杂 SQL、单位、唯一性语义和索引价值由 review 承接。
- 隔离数据库必须验证约束、删除、迁移及并发行为；未执行必须单列。合法/违规样例见 `apps/api/src/__tests__/quality-gates.spec.ts`。
- 命令登记见 ../reference/verification.md，不能以静态检查代替实际库状态。
