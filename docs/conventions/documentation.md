# 产出物写作规范

> 层：规范 · 时态：约束未来 · 失效：写作规范变更时

## 目的

让每篇文档都能回答什么情况下读我、违反我长什么样。避免产出读起来专业但无法执行的散文。

## 适用与不适用

- 适用：`docs/` 下所有现行文档、`AGENTS.md`。
- `docs/prd/` 仅适用本文件「PRD 产物规范」小节，不适用上方规范性骨架。
- 不适用：代码注释（见 `code-comments.md`）、git 提交信息（见 `../process/workflow.md`「提交信息」）。

## 结构要求

- 三元组必须位于第 3 行；缺三元组或位置不对即不合规，见 `../governance.md`「元数据要求」。 `DOC-3.1`
- 用户明确要求不设验证的规范可以省略「验证方式」一节，需在 `../decisions/` 以 ADR 留痕。

规范性文档按此骨架（三元组与篇数预算的唯一来源是 `../governance.md`，此处只给模板）：

```markdown
# 标题

> 层：规范 | 描述 · 时态：约束未来 | 描述现在 · 失效：<可判定条件>

## 目的（为什么存在，1-3 行）

## 何时读取（触发条件，可判定）

## 适用范围 / 不适用范围

## 规则（每条带强度词与判定边界）

## 验证方式
```

## 规则写法

强度词、禁用词、可判定性写法与规则 ID 格式以 `../governance.md`「规则质量要求」为唯一来源，此处不重复。

## 表格优先

对比、映射、判定矩阵用表格，不用段落罗列。表格迫使写作者明确列与列的关系。

## 长度与拆分

逐篇行数上限、篇数预算与拆分判据见 `../governance.md`「规模预算」「拆分判据」，此处不重复。

## 引用

- 引用其它文档用相对路径，并尽量指到具体小节或规则 ID。
- 引用命令只在 `verification.md` 维护；其它文档写见 `verification.md` 注册表。
- 引用代码路径必须真实存在；不存在时写待创建。

## 语言

- 正文中文；路径、命令、代码、标识符保留原文。
- 一个文档一个主题；标题不重复父级信息。
- 术语首次出现时给英文原文，之后统一用一个说法。

## PRD 产物规范

目录 `docs/prd/`，模板 `../prd/_TEMPLATE.md`；目录职责与预算豁免见 `../governance.md`「两层与目录」「规模预算」。

- PRD 有两种形态：扁平单篇与目录式，同一功能域不混用；章节以模板为准，无内容标「无」，不删节。目录式固定三类文件：`index.md`（门户与产品）、design.md（总体设计：架构、技术方案、文件结构、数据与接口）、`NN-<域>.md`（功能域规格，含 A 产品规格与 B 技术设计）；只允许一层，`index.md` 必须登记在 `../index.md`「功能交接主文档」。 `DOC-3.2`
- 命名：目录式主文档 `index.md`、总体设计 design.md、功能篇 `NN-<英文域>.md`（两位序号 + 域名，定稿后不复用、不重排）；扁平单篇只允许单次型 `YYYYMMDD-<英文短名>.md` 与演进型 `<英文短名>.md`。 `DOC-3.3`
- 职责分离：PRD 写产品设计、架构设计、技术实现与验收；技术取舍与被否决项写 ADR；实施进度、完成度与一次性事实不进入 PRD。
- 单一出处：数据表、接口、文件树的总览只在 architecture 写一次，功能篇只写本域明细；同一张表只有一个归属篇。
- 名称跟随需求演进：概述首句必须含功能中文名与英文短名括注（如「认证中心（auth）」）；名实不符时必须 `git mv` 改名并在版本记录留痕；目标用户或场景不同批时拆新篇。
- 演进型文档同时只有一个在途迭代：新需求先入「开放问题」，澄清后进「里程碑」与「范围」；方向性取舍写 ADR 并在版本记录行链接。
- 产品段（A 段、index）禁止实现词与代码路径；B 段禁止进度词；验收用复选框列表按功能分组，AC 编号全局唯一。
- 同一 PRD 的 index、design、NN-域共用同一版本号；整份 PRD 统一升版，禁止逐篇独立版本。
- 状态「已确认」只能由作者设置；「已上线」前置为收口验证通过且实现事实已进描述层（`../reference/architecture-overview.md`、`../index.md`「当前仓库事实」）。

## 反模式

| 反模式                            | 后果                                               |
| --------------------------------- | -------------------------------------------------- |
| 复制规则到多个文件                | 更新时漏改，产生互相矛盾的两个版本                 |
| `prd/` 层之外写未来会有的功能文档 | 读者无法区分已实现与设想；未来需求只进 `docs/prd/` |
| 用目录树代替职责说明              | 目录变化时文档立即过期                             |
| 把需求和技术执行规格混在同一小节  | AI 无法判断产品约束与实现约束的优先级              |
| 长篇背景铺垫                      | 抬高每次任务的固定阅读成本                         |
| 无标注的推测                      | 后续任务把推测当事实继承                           |

## 验证方式

- 纯文档改动：`pnpm check:docs` + `pnpm check:rules`（命令见 `../reference/verification.md`）。
- 新增文档：通过「拆分判据」与「生长规则」，并更新 `../index.md` 清单。
