# 文档治理

> 层：规范 · 时态：约束未来 · 失效：新增 ADR 修订本文件条款时

本文件定义 `docs/` 的角色、目录职责、元数据、拆分判据、规模预算与生长/删除规则。目标是**入口轻、规则稳、事实可追踪**。

## 角色

`docs/` 是**面向 agent 执行的工程契约层**：只承载 agent 每次任务必须遵守的约束、必须核对的事实、必须留痕的决策。读者优先级：**agent > 人**。任何为了人读得舒服而写的背景铺垫、教程、进度记录，不进入 `docs/`；解释性内容集中在 `docs/reference/architecture-overview.md` 一篇。

## 两层与目录

按内容时态分三层：**规范**（约束未来）、**描述**（描述现在）、**计划**（期望未来）。目录对应关系：

| 目录           | 层   | 只放这些                                       | 不放这些                       | 规模        |
| -------------- | ---- | ---------------------------------------------- | ------------------------------ | ----------- |
| `process/`     | 规范 | 任务过程规则：分级、推进循环、权限、红线、提交 | 代码风格、产物格式             | ≤ 2 篇      |
| `conventions/` | 规范 | 产出物规范：结构、契约、数据、前端、测试、注释 | 任务流程、现状叙述             | ≤ 120 行/篇 |
| `reference/`   | 描述 | 当前架构总览、命令注册表、规则→检查映射        | 未来计划、设计愿景             | ≤ 160 行/篇 |
| `prd/`         | 计划 | 产品设计、架构设计、技术实现与验收（三类文档） | 实施进度、决策论证、已完成事实 | 豁免        |

失效方式：规范只能由新的治理决定修改；描述随代码或配置变化失效；计划随实现落地或需求废弃失效。历史决策逐条记录在 `docs/decisions/`（ADR）。

## 拆分判据

新增、合并或拆分文档时，按三条判据判定；缺一即视为拆分错误，先改结构再写内容：

1. **单场景**：一篇只回答一类变更场景（建模块 / 改契约 / 改数据 / 写前端 / 写表单 / 写测试 / 写文档 / 权限 / 注释），篇内**规则小节**（含规则条目、不含「目的 / 何时读取 / 适用范围 / 验证方式 / 反模式」骨架节）≤ 7 个。
2. **单出处**：一条规则只在一篇定义；其它篇只引用路径与规则 ID，**不复述、不抄表、不抄目录树**。
3. **场景覆盖**：一次任务除入口两篇外默认 **≤ 5 篇**；新建带权限模块 **≤ 8 篇**。超出时先合并或重切，不允许靠多读解决。

反例（当前结构已修复，禁止回退）：把契约规则埋在架构总纲里；同一目录树抄进 4 篇；把规范正文只写在 ADR。

## 元数据要求

每篇**现行文档**（`AGENTS.md`、`docs/index.md`、`docs/governance.md`、`docs/process/*`、`docs/conventions/*`、`docs/reference/*`）的**第 3 行**（标题下第一个非空行）必须是三元组：

`> 层：规范 | 描述 · 时态：约束未来 | 描述现在 · 失效：<可判定条件>`

缺三元组或位置不对即不合规。`docs/decisions/*`（ADR）不要求三元组：头部以「状态 · 日期 · 级别」一行代替，格式见「决策记录」。

## 写入规则

- 过程规则 → `docs/process/`。
- 产物规范 → `docs/conventions/`。
- 当前事实与命令 → `docs/reference/`；命令只登记在 `verification.md`，其它文档只引用。
- 当前仓库事实（阶段、模块、命令状态）在 `index.md`「当前仓库事实」维护；其中的版本与命令由 `pnpm check:docs` 机检，不另建副本。
- 决策证据 → `docs/decisions/` 新建 ADR；**规范正文不得只存在于 ADR**，ADR 只写决定、被否决项与后果。
- 功能交付主文档 → `docs/prd/`；目录式固定 index / architecture / NN-域 三类，PRD 写设计与验收，技术取舍进 ADR，进度不进 docs。
- 一次性事实、临时绕坑 → 不写文档，写在提交信息或对话里；重复出现 ≥ 3 次再评估是否成为规则。
- `AGENTS.md` 只保留入口摘要与指针：每条 ≤ 1 行并给出唯一来源，不复制规范正文段落。
- 新建目录前先回答：现在有触发信号吗？没有则不加。

## 规模预算

**现行文档 ≤ 23 篇**，逐篇口径与行数上限（唯一来源，其它文档只引用）：

```
AGENTS.md（≤ 90 行）、docs/index.md（≤ 80 行）、docs/governance.md（≤ 150 行）
docs/process/*.md（≤ 120 行/篇）：workflow.md、boundaries.md
docs/conventions/*.md（≤ 120 行/篇）：architecture.md、contracts.md、persistence.md、authorization.md、
  naming.md、documentation.md、frontend.md、web-ui.md、web-ui-components.md、forms.md、testing.md、code-comments.md、
  code-quality.md、database.md、security.md、runtime.md
docs/reference/*.md（≤ 160 行/篇）：architecture-overview.md、verification.md
```

超出时先删除或合并，再讨论放宽。超过预算篇数即视为不合格。预算只约束现行规范 / 描述文档；`docs/decisions/`（ADR）不计篇数，逐条自包含；`docs/prd/`（计划层）豁免：不计篇数、不设行数上限、不要求三元组。

## 规则质量要求

一条规则可被接受，需满足：

1. **触发条件**：什么任务 / 什么文件下适用。
2. **强度词**：必须 / 应该 / 可以 / 禁止，四选一，不用“尽量”“适当”。
3. **可判定边界**：违反时的具体形态。
4. **验证方式**：机器检查或人工检查的具体动作；用户明确豁免的规范除外。
5. **可追踪**：机器可判定的规则必须有稳定 ID（沿用 `<前缀>-<组>.<序>`：既有 ID 保留，移动章节不改 ID，退役 ID 不复用；新增 ID 在所属前缀下递增登记），并登记在 `verification.md`「规则 → 检查映射」；纯人工判定规则按篇登记、可不加 ID。无 enforcement 的规则视为未落地。

反例：`保持代码简洁`（无判定标准）、`适当拆分组件`（无触发条件）、`注意文档同步`（无验证方式）——这类表述必须改写为可判定形式。

## 规范效力与事实记录

1. 已批准规范必须约束实现；既有代码、框架惯例、实现便利不得覆盖规范。AGENTS 是入口摘要，ADR 是决策记录；项目执行流程统一归 process，不另维护项目 skills 或重复规则。
2. 源码、配置与真实命令输出证明实际状态，禁止按规范目标编造已实现或已验证的事实。
3. 描述文档失实时修描述；实现违反规范时先修代码，禁止自动修改规范迁就实现。
4. 规范确需变更时，必须先确认条款、影响面、检查、迁移和回滚，再更新所属规范、ADR、检查及实现。

## 冲突处理

1. 规则冲突必须明确定位，先提交替代条款，禁止选择对实现更方便的规则。
2. 检查漏报必须修代码并补回归检查；误报必须用合法样例证明，修检查后仍须拒绝违规反例。
3. 例外必须在规则所属文档列出路径、允许行为、理由、验证和退出条件；禁止以永久白名单掩盖迁移欠账。
4. 规则映射必须区分完整、部分和待落地；部分覆盖须列明人工审查项，不能仅凭检查文件存在宣称规则已执行。
## 检查与迁移治理

- 各规范的修改者必须在任务收口列规则 ID、覆盖程度、实际命令、人工项和未验证项；批准人负责规则/例外生效，环境管理员负责远端和发布保护核验。
- 新机器规则必须有合法、违规和边界样例；解析失败、测试未收集、环境缺失与过期结果必须显式失败或报告未验证，禁止静默通过。
- 自动检查适用范围必须写明；新增规则按变更范围逐步启用，既有门禁保持。禁止自动接受现状、目录级豁免或擅自创建历史基线。
- 历史基线确需引入时必须另经 ADR，逐问题登记规则、位置、责任与期限；临时例外登记在所属规范，过期必须处理，基线不得自动增长。
- 增量检查是开发反馈，不替代全仓检查；检查器修改必须保留能拒绝既有违规的样例。结果必须绑定基准、内容摘要和检查配置，后续改动使结果失效。
## 生长规则

新增文档或规则条目，需同时满足：

1. 有明确触发条件（什么任务下要读它）。
2. 有可判定边界（违反长什么样）。
3. 有验证方式（谁能检查、怎么检查）。
4. 不重复已有文件的职责。

四条缺一，不进文档，先记为待办或决策候选。

## 删除规则

出现以下任一情况，删除或合并而非继续维护：

- 引用的路径 / 命令已不存在且无人修。
- 连续两个阶段没有被任何任务读取（入边为 0 的游离文档优先处理）。
- 与另一个文件职责重叠。
- 被新的治理决定取代。

删除时同步更新 `docs/index.md` 与 `AGENTS.md` 的引用。**只增不减的文档体系必然腐烂。**

## 维护节奏

| 时机                | 动作                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------- |
| 每次收口            | `git status` / `git diff` 自查；修掉本次造成的文档偏差；跑 `pnpm check:docs` 并记录真实输出   |
| 新增目录 / 规则     | 检查「拆分判据」三条 +「生长规则」四条                                                        |
| 阶段迁移            | 追加 ADR，同步 `AGENTS.md` 阶段事实；跑一次漂移审计（`pnpm check:docs` + `pnpm check:rules`） |
| 发现断链 / 失效命令 | 立即修；不能立即修则标注 `待落地` 并记入 `verification.md`                                    |

## 检查入口

文档结构与规则落点的唯一入口是三条命令，实现分别在 `scripts/checks/docs.ts`、`scripts/checks/rules.ts` 与 `scripts/checks/protected.ts`；命令登记与提交门禁见 `verification.md`，本文件不复制命令正文：

- `pnpm check:docs`：ADR 状态/编号及横切 spec 存在性、现行文档篇数、逐篇行数上限、三元组三字段与第 3 行位置、根目录无未纳管文档、`index.md` 清单完整、markdown 引用不断链、文档引用的代码路径存在、`docs/prd/` 文件命名与模板章节完整性、`verification.md` 注册表登记的 pnpm 命令真实存在。
- `pnpm check:rules`：规则 ID 双向（文档出现的 ID 已登记、登记的 ID 能在文档命中）、稳定 ID 格式、唯一性及所属前缀、前端与命名机检。
- `pnpm check:protected`：检查设施和配置变更有明确治理记录，完整保护范围见 `reference/verification.md`。

两条命令全绿并记录真实输出，才算文档收口；人工抽查不替代命令。

## 决策记录

治理级决定以轻量 ADR 逐条记录在 `docs/decisions/`：一条决定一个文件，命名 `NNNN-英文短名.md`，编号递增追加。

- 正文三段：决定 / 被否决的选项 / 后果，被否决项必须写明否决理由。
- 头部一行 `> 状态：已接受 | 已取代 · 日期：YYYY-MM-DD · 级别：L0-L3`；取代关系写入被取代文件的「状态」行。
- ADR 是记录不是规范：不计篇数、不要求三元组、`pnpm check:docs` 不把 `decisions/` 计入现行文档预算，但检查 ADR 编号与状态头；规范正文不得只写在 ADR。
- 决定正文不在本文件内追加；新 ADR 落地时同步修订被取代 ADR 的「状态」行、本文件受影响条款及 `AGENTS.md`、`docs/index.md` 的引用。
- 路由：想知道某个取舍为什么这么定，先 `ls docs/decisions/` 按文件名定位，再读对应文件。
