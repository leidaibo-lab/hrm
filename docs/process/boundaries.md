# 边界：权限分层与红线

> 层：规范 · 时态：约束未来 · 失效：权限模型变更时

## 权限分层

| 级别       | 范围                                                     | 授权方式               |
| ---------- | -------------------------------------------------------- | ---------------------- |
| 自由       | 读任何文件、在 `docs/` 与源码中新增/修改、跑本地只读命令 | 无需确认               |
| 需声明     | 跨包契约变更、依赖增删、构建配置                         | 先说明方案再执行       |
| 需明确指令 | 删除文件、`git` 历史操作、推送、发布、外部系统真实写入   | 必须有用户当次明确指令 |

需明确指令清单**不因任务看似显然而豁免**。删除一个看起来没用的目录，必须先得到指令。

文档结构 / 流程 / 门禁变更属 L3，先确认具体条款与回滚；同一方案已经确认后无需重复确认，见 `workflow.md`。

## 红线

以下行为一律禁止，无例外：

1. 编造命令、版本、路径、测试结果。
2. 删改用户未授权范围内的文件；覆盖用户已有改动。
3. 把未执行的命令报告为已运行。
4. 在文档中写入与本仓库事实不符的栈、脚本或结构，且不标注为待落地/推断。落点：`pnpm check:docs`（栈版本、脚本命令、代码路径机检；「待落地 / 推断」标注由 review 复核）。 `BND-2.1`
5. 提交含密钥、令牌、个人凭据的内容。
6. 为让检查通过而放宽检查本身（改断言、删测试、绕过 lint）。落点：`pnpm check:protected` 检查设施保护（`scripts/checks/protected.ts`）。 `BND-2.2`

第 6 条尤其重要：**验证的存在意义是拦截改动，不是被改动绕过。**

## 事实确认（防幻觉）

四类信息不得凭印象写出，必须先现场确认：

| 类型 | 确认方式                              | 禁止行为                  |
| ---- | ------------------------------------- | ------------------------- |
| 命令 | `verification.md` 注册表 + 实际存在性 | 写应该可以 `pnpm run xxx` |
| 版本 | `package.json` / lockfile / 实际输出  | 按训练记忆写版本号        |
| 路径 | `ls` / 文件搜索实际存在               | 假设目录布局              |
| 行为 | 读源码                                | 按框架常识推断本项目实现  |

版本可从 `node_modules/.pnpm` 目录名**推断**，但只是线索，不是已验证事实；落地前标注推断。

## 不确定时

按此顺序选择：

1. 只读不写，先问。
2. 写出假设并标注 `假设：`，继续推进可回滚的部分。
3. 缩小任务范围到确定的部分，把不确定部分单独列出。

不要用我理解用户大概想要来填补空档。

## 破坏性操作前置检查

删除、移动、批量重写前：

1. 打印解析后的**绝对路径**，确认是目标本身。
2. 确认范围（`git status` 是否有未跟踪相关文件）。
3. 确认可回滚（是否有 git 跟踪 / 备份）。
4. 变量路径必须用 `${VAR:?}` 保护，禁止未校验的变量拼接路径。

## 与用户指令的关系

- 用户的当次明确指令可以授权需明确指令级别的操作。
- 但用户指令**不能**授权红线 1、3、5、6 类行为（编造、谎报、泄密、绕过检查）。
- 用户指令与本文件规则冲突且不涉及红线时：执行指令，收口时说明偏差。

## 拒绝与上报

- 无法完成时直接说明卡在哪，不要产出半成品并包装成完成。
- 需要外部凭据、网络、生产环境时，报告具体缺口，不要尝试猜测性绕过。
- 发现既有代码或文档存在越界/不安全模式时，报告而不是顺手修复。
