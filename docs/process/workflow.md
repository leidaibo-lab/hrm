# 工作流：任务分级与推进循环

> 层：规范 · 时态：约束未来 · 失效：治理决定变更流程时

## 为什么分级

不同任务需要不同强度的流程。全流程套在改一个错别字上会让人绕开流程；无流程套在跨模块重构上会产出不可验证的改动。分级是为了让重流程只在真需要时出现。

## 任务分级

| 级别      | 判定标准                                           | 流程要求                | 验证要求                |
| --------- | -------------------------------------------------- | ----------------------- | ----------------------- |
| L0 只读   | 只回答问题、不写文件                               | 直接回答                | 引用文件路径            |
| L1 单点   | 改 1–3 个文件、不改外部契约、可独立回滚            | 读取顺序 + 直接实现     | 与改动匹配的最小验证    |
| L2 跨模块 | 跨 app/package、改共享类型或契约、改动影响多调用方 | 先列影响面清单 → 再实现 | 全量相关验证 + 边界说明 |
| L3 高风险 | 改文档结构、CI、依赖、构建配置、破坏性变更         | 先写方案并取得确认      | 全量验证 + 回滚路径     |

判定取**最高**符合项。不确定时往上一级。

**规范接触面同样参与判定**：改动虽小但新增/修改了规范条款涉及的结构（文件角色、接口形态、权限点、测试放置），验证项按对应规范条款执行，不因 L1 而省略。

## 推进循环

```
读（AGENTS → index → 按需）
  ↓
定位（git status → 目标区域内 grep）
  ↓
声明（这次要改什么、不改什么、怎么验证）
  ↓
核对适用规则与检查覆盖 → 实现（最小改动面）
  ↓
验证（查注册表挑命令，跑，记录真实输出）
  ↓
收口（git status/diff 自查 + 文档偏差修正 + 汇报）
```

### 声明的价值

开工前用 3–5 行说清改什么 / 不改什么 / 怎么验证。这不是仪式：**它把隐性假设变成可被反驳的显式陈述**，也让 L2/L3 任务在动手前就能被拦住。

## 提交信息

触发：创建任何 git 提交时。

1. 格式必须为 `<type>(<scope>)?: <主题>`；type 限枚举：feat、fix、docs、style、refactor、test、build、ci、chore。
2. scope 必须是受影响的包或目录名（api、web、shared、docs）；无明确单一归属时省略。
3. 主题用中文祈使语气、结尾不加句号、≤ 72 字符。
4. 正文承载为什么与一次性事实；禁止只罗列文件清单。
5. 破坏性变更必须在主题加 `!` 或正文含 `BREAKING CHANGE:` 与影响说明。
6. 一次提交只承载一个目的；纯格式化与逻辑变更禁止混在同一提交。
7. 验证：type/scope 枚举由 commit-msg hook 强制（`commitlint.config.ts`，scope 为项目自定义枚举；commitlint 的 header 上限 100 字符，规范更严的 72 字符与中文祈使由 review 承接）；门禁内容见 `../reference/verification.md`「提交门禁」，本文件不复制门禁命令。

## 退出条件

一个任务算完成，必须同时满足：

1. 声明的范围全部落地，范围外没有顺手改动；列明适用规则及机器/人工验收结果。
2. 验证命令真实执行过，且引用的是真实输出。
3. `git status --short` 检查过，没有意料之外的文件。
4. 实现违规必须修代码，禁止反改规范或扩大白名单；检查漏报补回归，误报须保留违规反例。若改了文档结构或规则，相应文档已同步；文档偏差修正后必须跑 `pnpm check:docs` 并记录真实输出。
5. 汇报中写清：改了什么、验证了什么、没验证什么；文档改动需附 `pnpm check:docs` 的真实输出。

**只满足 1–3 不足以宣称完成**：第 4/5 项是对声称完成但文档已分叉的防护。

## 生成与验证反馈

1. 每次完成可独立验收的逻辑批次必须执行变更检查，并按计划执行类型与相关行为测试；违规必须在当前批次修复，再进入下一批次。命令唯一登记于 verification.md。
2. 开发模式覆盖暂存、未暂存和新文件；提交模式检查实际暂存快照；CI 必须使用明确目标基准，无法确定影响面时扩大到包或全仓。
3. 保存监听只运行快速检查；批次收口运行完整计划。监听必须串行、合并连续改动并使过期结果失效，禁止把上次通过用于新内容。
4. 检查结果必须区分通过、违规、执行异常、未验证、人工待确认，并记录基准、内容摘要、命令和退出状态；机器通过不能替代人工验收。
5. 提交和 CI 保留现有门禁；发布前必须另附构建、数据库升级、关键链路及恢复证据，环境不足不得发布完成声明。

## 中途失败与阻塞

- 验证失败先判断是改动错还是命令不存在/环境缺失；后者不要伪装成前者。
- 同一问题连续两次修复失败，停下来重新描述问题，不要第三次盲试。
- 依赖缺失、权限不足、需要真实外部写入 → 停止并上报，见 `boundaries.md`。

## 什么不算工作流

以下不属于本工作流管辖，不要为它们编流程：格式化细节、命名偏好、注释的格式细节。注释的契约要求见 `../conventions/code-comments.md`；格式细节交给 lint/格式化工具，见 `../reference/verification.md`。

## 与规范演进的关系

发现规则需要变更时：规范条款的修改走 L3（方案 + 确认 + ADR）；新增规则条目需要走 `../governance.md` 的生长规则与拆分判据，避免规则集无序膨胀。

## 带权限模块实施顺序

1. 登记 shared 权限目录，再按 domain 实体/端口 → application → infrastructure → DTO/controller → module 装配；结构规则见 architecture、命名见 naming、权限见 authorization。
2. schema 变化审查迁移、查询、mapper、实体、读模型及消费方；数据约束见 persistence。迁移与数据库验证按需本地执行，不进入 CI。
3. 按 testing 覆盖领域不变量、应用行为、403 拒绝和相关契约；替身仅放在依赖边界。
4. 接口变化离线导出 OpenAPI 并生成 SDK，再实现 feature api/keys → 表单或交互 hook → 业务组件 → feature 出口 → 页面消费；规则见 contracts、frontend、forms。

## 收口执行顺序

1. 对照实际 diff 列适用规则，按 verification 的矩阵执行最小充分验证；人工条款逐项审查，不能用机器通过代替。
2. L2/L3 必须按规则 ID 报告 PASS/FAIL/不适用及证据；没有适用条款时说明原因，未运行与跳过单列。
3. 实现违规修代码、检查漏报补回归、描述失实修描述；规范变更必须已有确认。检查设施变化按批准 ADR 更新保护基线。
4. 检查工作区与空白错误，最终报告改动路径与关键行为、实际命令与输出、未验证项及风险；禁止把欠缺验证包装成完成。
