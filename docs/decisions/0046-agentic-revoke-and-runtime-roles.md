# ADR-0046 agentic S1 回填撤销与 runtime 命名两层封闭表

> 状态：已接受 · 日期：2026-11-16 · 级别：L3

## 决定

补齐 PRD-AGENTIC §16.1 剩余项中的「S1 字段回填可撤销」，并把 ADR-0044 新增的 runtime 执行角色按「两层封闭表」落进命名规范，同时更新因此受影响的检查设施。

- **S1 撤销**：新增 `POST /agentic/tickets/:id/writeback/revoke`。撤销不原地改字段，也不删除历史产物；以上一版本产物内容追加一个新版本并再次写回声明的字段，版本链只增不改，撤销本身可回放。权限沿用 `ticket:decide`，审计动作 `artifact.revoke`。
- **命名两层封闭表**：通用角色保持 18 项不变，业务域只能复用、不得新增后缀；`agent` / `workflow` / `tool` / `scorer` 作为「runtime 执行角色」单独成 4 项全局封闭子表，仅允许出现在 `modules/*/infrastructure/runtime/{agents,workflows,tools,scorers}/`。四项跨域共用同一套，不随域派生；新增或调整任一层角色仍需同改对应表、白名单测试与 ADR（NAM-4.1）。
- **工作流与质量门禁**：澄清流程改为 Mastra Workflow（装载上下文 → 角色出稿 → 校验 → 评分 → 人工分支标记），质量分低于 0.7 时应用层追加人工复核关注，不静默交付。
- **检查设施同步**：`apps/api/src/__tests__/architecture.spec.ts` 放行 runtime 四角色，并补正/负回归用例钉住边界（`application/` 下的 `.agent.ts`、`runtime/` 下自定义后缀、`infrastructure/` 下域专属后缀均拒绝）；`permission-matrix.snap` 增加撤销端点。两份文件均为受保护检查设施，基线按本 ADR 更新。

## 被否决的选项

- **原地覆盖字段或删除产物**：破坏审计链与回放能力，撤销后无法证明撤销前的内容。
- **撤销走独立的新表**：现有 `agentic_artifacts` 已是追加式版本链，再加一套撤销表会形成第二真相源。
- **把四个执行角色并入通用角色表**：会让角色表按域生长，等于给每个领域开自定义后缀的口子；本次改为独立全局子表。
- **用目录表达职责、不新增后缀**：文件名失去自解释能力，且要回改已接受的 ADR-0044 与 PRD 命名条款，收益低于成本。
- **评分器调用模型 judge**：澄清质量可用确定性规则判定，V0 引入模型 judge 只会增加成本与不稳定性。
- **不做 protected 基线更新、直接放宽检查**：等于绕过检查设施，违反治理口径。

## 后果与回滚

- 撤销接口让「确认后回填」具备可逆路径；代价是版本链会多出撤销版本，控制台按版本号可读，无需特殊展示。
- 命名分两层后：通用角色表仍只对业务域开放 18 项；runtime 四角色是全局技术角色，任何域有 runtime 层都复用它，新增第五个 runtime 角色必须走 ADR。
- 澄清质量分依赖确定性规则；规则调整需要同步更新评分器测试与 PRD 验收标准。
- 回滚：删除撤销端点与 `revokeWriteback`、移除 runtime 四个角色目录与子表、`architecture.spec.ts` 恢复原白名单、命名表恢复单层 18 项、按仓库历史恢复两份检查设施基线；已写入的产物版本保留，不参与新流程。
