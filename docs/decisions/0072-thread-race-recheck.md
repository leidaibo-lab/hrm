# ADR-0072 Thread ensureOpen 并发竞态回查

> 状态：已接受 · 日期：2026-11-16 · 级别：L2

## 问题

本地并发压测（同一 `message_id` 50 请求 / 20 并发）发现：唯一键去重生效（仅 1 条触发），但 17 个请求返回 500。日志为
`agentic_threads_sourceType_externalKey_key` 唯一约束冲突，位置在 `ThreadPrismaRepository.save` 的 `upsert(where: id)`。

根因：`ThreadService.ensureOpen` 先按外部键查、未命中再生成随机 id 保存；两个并发请求都未命中，随后都尝试插入同一 `(sourceType, externalKey)`，后插入者失败。

## 决定

`ensureOpen` 保存失败时回查外部键：

- 若另一请求已创建，返回该线程，调用方继续处理；
- 回查仍为空则抛出原错误，不吞掉真实故障。

不改仓储 `upsert` 的 `where`：`id` 是主键，改成复合键会影响更新语义；在用例层做一次补偿查询更小。

## 被否决的选项

- **数据库 advisory lock / 分布式锁**：为一次插入引入额外锁成本与故障面。
- **捕获 Prisma 错误码**：application 层不应依赖 Prisma 类型；回查成功即证明是竞态。
- **先插入后查**：仍会撞唯一键。

## 验证

2026-11-16 本地隔离库 + 真实 API：

- 修复前：50 请求 / 20 并发 → 33×200、17×500，触发仍仅 1 条。
- 修复后：同样 50 请求 / 20 并发 → **50×200**，触发仍仅 1 条。
- 单测：`ThreadService.ensureOpen` 保存抛唯一冲突后回查并复用已创建线程。
- 唯一消息 100 请求 / 20 并发：100×200，耗时 183ms。

未验证：多副本同时首见同一线程（本次为单进程并发）；真实数据库隔离级别差异。

## 后果与回滚

- 竞态时多一次查询，正常路径无额外开销。
- 回滚：移除 catch 回查，重新出现 500；不建议。
