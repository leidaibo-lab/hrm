# 表归属声明与上下文前缀

> 状态：已接受 · 日期：2026-11-16 · 级别：L3

## 决定

物理表名默认保持 `<实体复数>`，不带任何归属前缀；新增或修改的 model 首行必须声明 `// 域: <上下文>`，上下文必须登记在 `docs/conventions/database.md` 的「上下文与物理前缀」表中。登记了前缀的上下文，其全部表必须使用 `<上下文>_`；未登记前缀的上下文，表名不得使用任何登记前缀，也不得用自身域名作前缀（因此 `iam_users` 违规）。新增上下文须先登记并附 ADR。

登记表由 `scripts/checks/lib/contexts.ts` 解析，`scripts/checks/database.ts` 在变更模型上执行 `DB-4.2`，`scripts/checks/rules.ts` 校验登记表自身（唯一性、前缀与上下文一致、模块存在、禁用技术/产品名前缀）。存量模型不回填，谁修改谁补声明。

## 被否决的选项

- **全库按归属加前缀**（`iam_users` / `platform_audit_logs`）：无迁移收益，却把表名绑到会变的代码目录；共享内核被标成某模块私有，诱发重复建模。
- **只做前缀登记、不要求域声明**：前缀是自愿的，新表仍可无主平铺，治不了失控。
- **PostgreSQL schema 隔离**：授权与备份边界更彻底，但需 Prisma multiSchema、迁移与团队认知成本；留到 agent 域真正独立部署时再单独决定。
- **表名 COMMENT**：`\dt+` 可见归属，但每张表都要在迁移里手写并维护，现阶段收益低于成本。

## 后果

`DB-4.2` 与 `PER-4.1` 共同约束命名：读 SQL 时 `agent_` 可辨上下文，`users` 等唯一表名保持简洁；新表必须回答归属，新增上下文成本是一次 ADR。前缀不提供授权、备份或拆库隔离。回滚为还原 `database.md`、本 ADR、检查脚本与测试、`verification.md` 映射及保护基线，无 DDL、无数据影响；已在 schema 中补写的 `// 域:` 声明可保留。
