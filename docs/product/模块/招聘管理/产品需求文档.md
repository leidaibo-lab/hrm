# HRM 人资管理系统——招聘管理模块 MVP 产品需求文档

- **版本**：0.2
- **状态**：需求草案，已补充关键业务决策，待团队评审
- **适用范围**：技术部前端招聘试点
- **文档依据**：[范围说明](范围说明.md)、[产品决策记录](../../产品探索/产品决策记录.md)、[权限与数据治理规范](../../公共规范/权限与数据治理规范.md)、[字段与表单校验规范](../../公共规范/字段与表单校验规范.md)

## 1. Summary

本项目建设 HRM 人资管理系统的招聘管理模块 MVP，承接飞书职位发布完成后的职位建档、候选人筛选、邀约、面试、评价和录用决策。飞书继续负责招聘需求创建、审批、职位发布和关闭，HRM 成为候选人及面试协作的管理系统。

一期通过 HR 人工登记职位和导入 Boss 直聘简历，验证技术部前端招聘的完整业务闭环。系统重点解决候选人状态不透明、面试评价不及时和招聘事项长期未推进的问题。

## 2. Contacts

| 角色 | 责任 | 参与内容 |
| --- | --- | --- |
| 业务负责人/老板 | 飞书招聘需求审批人 | 继续在飞书完成审批，不要求使用 HRM |
| HR成员/招聘专员 | 业务负责人、核心用户 | 建档、导入候选人、邀约、创建面试、确认录用和维护全局招聘数据 |
| 用人负责人 | 招聘协作负责人 | 初筛、指定面试官、维护面试决策和维护面试模板 |
| 面试官 | 评价提供者 | 查看候选人完整简历、参加面试、提交结构化评价 |
| 系统管理员 | 平台管理员 | 管理用户、部门、角色、字典、软删除恢复和审计记录 |
| 前端团队 | 产品与研发团队 | 负责试点实施、验证和反馈收集 |

具体姓名、评审时间和设计稿链接待项目组补充。

### 2.1 术语约定

- **HR成员**：系统业务角色。拥有该角色的用户可以按权限执行招聘管理操作，并查看全公司招聘数据。
- **HR负责人**：职位级责任字段。每个职位设置一名主责 HR，负责该职位的候选人跟进、邀约、面试创建并接收该职位的长期未推进提醒。最终录用由拥有 HR成员角色的授权用户确认，默认可由 HR负责人执行。
- HR负责人必须是 HR成员；HR成员不等于某个职位的 HR负责人。
- **用人负责人**：系统业务角色，同时是职位级主负责人。每个职位必须指定一名用人负责人；该角色决定其所属部门招聘数据的查看和初筛、决策等操作权限。
- **面试官**：系统业务角色，同时是面试级参与人。面试官不作为职位固定字段，而是在每一轮面试中单独指派，可以一次指定多人，也可以临时更换。
- 一个用户可以同时拥有 HR成员、用人负责人和面试官等多个业务角色；角色决定权限，职位或面试上的人员指派决定具体责任范围。

## 3. Background

### 3.1 现状

- 招聘需求创建、审批和职位发布已经在飞书运行，老板不方便切换到新的审批平台。
- 候选人简历来自 Boss 直聘，HR成员需要把简历和候选人信息录入可持续维护的系统。
- 面试评价目前主要以文案记录，候选人阶段、面试安排和后续决策不够集中。
- HR、用人负责人和面试官需要看到不同范围的招聘信息，但目前缺少统一的待办入口。

### 3.2 为什么现在做

团队希望通过真实业务实践全栈能力，公司也缺少招聘管理系统。招聘流程已有稳定的飞书前置流程，适合把范围收敛到“职位发布后到录用决策”的完整闭环。

### 3.3 约束

- 一期不复制飞书审批，不建设自建审批流。
- 一期不接入飞书 API、飞书日历、飞书消息和 Boss 直聘 API。
- 一期没有历史数据迁移。
- 简历和面试评价仍属于敏感人事数据，必须落实权限、审计和软删除。
- 面试时间以 HRM 记录为准；HR 负责在飞书日历发生变化后更新 HRM。

## 4. Objective

### 4.1 产品目标

在不改变飞书招聘前置流程的前提下，让 HRM 成为技术部前端招聘的唯一协作入口，完整追踪候选人从导入到录用、淘汰或放弃的过程。

### 4.2 试点结果

以下结果作为 MVP 验收结果，正式效率指标后置：

1. 试点职位都能关联飞书审批申请链接，并包含完整的职位必填信息。
2. 试点新增候选人都能关联一个职位，记录来源、简历、导入人和导入时间。
3. 候选人只能按授权状态流转，关键操作均能追溯到操作人和时间。
4. 每场面试都能在 HRM 中记录时间、轮次、面试官和结构化评价。
5. HR、用人负责人和面试官能在工作台看到自己需要处理的事项。
6. 长期未推进候选人按规则提醒职位 HR负责人和用人负责人，且不会提醒未参加过面试的候选人。
7. 试点验收中的越权查看、下载、修改和录用操作全部被系统阻止。

### 4.3 后续观察指标

试点阶段建立基础指标基线，同时保留审计和业务操作日志；指标口径、采集方式和一期通过门槛见[指标与试点基线](../../指标与试点基线.md)。正式埋点体系、独立看板和跨模块经营指标不属于一期范围。

## 5. Market Segment(s)

本产品服务的是需要共同推进内部招聘的人，而不是外部候选人。

| 用户 | 核心任务 | 主要约束 |
| --- | --- | --- |
| HR成员 | 把已发布职位和 Boss 直聘候选人建档，推动流程并确认最终录用 | 需要全局视角，不能重复维护飞书云盘和表格 |
| 用人负责人 | 判断候选人是否进入面试，安排面试官并做招聘决策 | 需要看到本部门全部招聘数据和完整简历 |
| 面试官 | 在面试前了解候选人，在面试后快速提交评价 | 只能处理授权范围内的面试和评价 |
| 系统管理员 | 维护账号、组织、字典、权限和审计 | 不因平台管理员身份自动获得全部业务数据 |
| 老板 | 审批招聘需求和查看飞书流程 | 一期不需要登录 HRM |

## 6. Value Proposition(s)

### 6.1 对 HR

- 一个位置查看全局职位、候选人、待评价和逾期事项。
- 简历直接进入 HRM，不再以飞书云盘作为中转。
- 状态、邀约、面试和录用记录集中保存，减少重复追问。

### 6.2 对用人负责人

- 直接查看本部门候选人和完整简历。
- 从工作台处理初筛、待决策和逾期事项。
- 用结构化评价和面试模板降低决策遗漏。

### 6.3 对面试官

- 从工作台直接进入自己的面试和候选人详情。
- 使用少量固定字段加文字补充提交评价。
- 在允许范围内查看同部门、同职位的其他评价。

### 6.4 相比当前做法的改善

HRM 不替代飞书审批，而是补齐发布职位后的协作空白。它把招聘主状态、面试安排和评价从分散文案变成可追踪记录，并用提醒推动责任人处理阻塞事项。

## 7. Solution

### 7.1 UX / 用户流程

#### 端到端流程

```text
飞书创建需求 -> 审批 -> 发布职位
                         |
                         v
             HR 在 HRM 创建职位
                         |
                         v
       HR 导入 Boss 直聘简历，进入待筛选
                         |
       HR 推荐 -> 初筛（待用人负责人判断）
                         |
                 用人负责人初筛通过
                         |
                       待邀约
                         |
          HR 记录招聘平台答复为“同意”
                         |
                 HR 创建面试
                         |
       用人负责人指定面试官，记录面试时间
                         |
            面试评价 -> 待决策
                         |
          HR 确认录用 / 淘汰 / 放弃
```

#### 主要页面

1. 登录、首次改密和账号状态页。
2. 角色工作台：待办、逾期面试、待评价和长期未推进候选人。
3. 职位列表与职位详情：来源、状态、负责人和候选人进度。
4. 候选人列表与详情：简历、阶段、邀约、面试、评价和变更记录。
5. 面试模板和字典配置页。
6. 用户、部门、角色和审计记录管理页。

设计稿暂缺，交互稿需要覆盖空状态、无权限、关闭职位、重复候选人、面试取消和未提交评价等状态。

### 7.2 Key Features

#### 7.2.0 公共规则引用

本模块遵循[字段与表单校验规范](../../公共规范/字段与表单校验规范.md)、[权限与数据治理规范](../../公共规范/权限与数据治理规范.md)。本 PRD 只记录招聘管理特有的字段、流程和例外，不重复维护跨模块规则。

#### A. 账号与组织

- 使用 HRM 独立账号密码登录，不直接复用飞书组织架构。
- 管理员创建用户并设置临时初始密码；首次登录强制修改。
- 管理员可以重置密码；重置后下次登录再次强制修改。
- 一个用户可以绑定多个业务角色，业务权限按角色合并。
- 管理员负责用户、部门、职位负责人和角色维护。
- 禁用或离职用户禁止登录；历史记录保留原操作人和历史权限关系。

#### B. 职位建档与状态

HR成员只能为飞书职位发布完成后的职位建档。必填字段如下：

| 字段 | 规则 |
| --- | --- |
| 职位名称 | 必填 |
| 部门 | 必填，决定业务数据范围 |
| 招聘人数 | 必填，正整数 |
| 用人负责人 | 必填，每个职位一名主负责人 |
| HR 负责人 | 必填，每个职位一名主责 HR成员 |
| 职位类型 | 必填，使用字典 |
| 工作地点 | 必填，使用字典 |
| 飞书审批申请链接 | 必填，作为来源凭证和追溯入口 |
| 发布时间 | 必填 |

HRM 职位状态包括“可招聘”和“已关闭”。飞书关闭职位后，HR成员手动将 HRM 职位调整为已关闭，禁止新增候选人，但不影响已有候选人的面试、评价、待决策和录用。飞书重新打开后，HR成员手动恢复 HRM 职位为可招聘。

#### C. 候选人和简历

候选人由 HR成员从 Boss 直聘取得后直接人工导入 HRM，不经过飞书云盘。必填字段为姓名、联系方式、简历、来源渠道和应聘职位。一个候选人一期只关联一个应聘职位。

系统记录来源标识、导入人、导入时间和状态历史。没有联系方式不能录入。导入时按标准化后的姓名和联系方式提示重复：姓名和联系方式一致为强重复；仅姓名相同不判重；联系方式相同但姓名不同提示 HR 判断。默认重复阈值为一年，以最后一次面试时间计算。

HR 确认合并后，新记录覆盖旧简历和面试记录，旧记录软删除并保留合并审计。

#### D. 候选人阶段和邀约

候选人阶段只允许正向推进，不允许回退。淘汰和候选人放弃不可恢复。最后一轮面试评价未全部提交时，候选人保持“面试中”，不能进入“待决策”。

| 当前阶段 | 下一阶段 | 可执行角色 | 关键条件 |
| --- | --- | --- | --- |
| 待筛选 | 初筛、淘汰、候选人放弃 | HR成员 | HR成员完成资料检查并推荐，或记录终止原因 |
| 初筛 | 待邀约、淘汰、候选人放弃 | 用人负责人；HR成员可记录候选人放弃 | 用人负责人初筛通过后进入待邀约；不通过进入淘汰；待补充仍停留在初筛 |
| 待邀约 | 面试中、淘汰、候选人放弃 | HR成员 | 招聘平台答复为同意后创建面试 |
| 面试中 | 待决策、淘汰、候选人放弃 | 用人负责人、面试官；HR成员可记录终止状态 | 当前配置的最后一轮面试完成且该轮被指派面试官的评价全部提交，或记录终止原因 |
| 待决策 | 录用、淘汰、候选人放弃 | HR成员、用人负责人、面试官；录用仅 HR成员 | HR成员确认入职后录用 |
| 录用、淘汰、候选人放弃 | 无 | 无 | 终止状态 |

邀约状态为待邀约、邀约中、同意、拒绝、失联。HRM 只记录 HR成员在招聘平台上的邀约结果；状态变更必须填写备注。只有“同意”才能创建面试。

公司取消面试时保留候选人原阶段并记录公司取消原因；候选人取消或拒绝时区分记录为候选人放弃。公司取消不重新邀约，也不重置提醒计算。

#### E. 面试与评价

- 面试由 HR成员创建，用人负责人指定本轮面试官。
- 面试轮次按安排面试时选择的招聘角色和面试职级配置；招聘角色和面试职级不是职位必填字段。
- 面试模板由用人负责人维护；轮次包含名称、顺序、角色/职级、默认时长、评价模板和是否必经。
- 安排面试时必须选择招聘角色和面试职级；系统保存匹配模板、评价模板和关键配置快照，后续模板修改不改变已创建面试的历史。
- 单个职位允许临时增加或减少轮次；面试官按轮次指定，可以一次指定多人，也可以临时更换。
- 改期只更新 HRM 中的面试时间；面试官更换只更新面试官；一期不与飞书日历同步。
- 评价包含面试结论、少量评价维度、是否推荐、风险项和文字补充。
- HR成员和用人负责人可修改评价；面试官不能修改其他评价。提交后的修改必须审计。

#### F. 工作台与提醒

| 角色 | 工作台重点 |
| --- | --- |
| HR成员 | 全局招聘、待处理评价和逾期面试；职位 HR负责人负责跟进该职位的长期未推进候选人 |
| 用人负责人 | 所属部门全部职位、候选人、待初筛和待决策事项 |
| 面试官 | 自己的面试、待评价事项和评价历史 |

工作台支持直接进入候选人详情、记录邀约、安排面试、补交评价和处理逾期事项。

候选人完成最后一轮面试且该轮被指派面试官的评价全部提交、进入待决策后，开始计算长期未推进提醒。按东八区工作日每 3 个工作日提醒一次，通知该职位的 HR负责人和用人负责人；同一候选人每天最多提醒一次，状态操作不重置计算，待决策仍继续提醒。没有完成过任何面试或评价未提交的候选人不提醒，录用、淘汰和放弃后停止提醒。提醒只在 HRM 内产生。其他 HR成员可通过全局工作台查看，但不默认收到该职位的提醒。

#### G. 权限、软删除与审计

本模块的操作级权限和数据范围如下。批量导出一期对所有角色关闭；下载权限不因拥有查看权限自动获得。

| 角色 | 数据范围 | 查看 | 创建/修改 | 下载 | 导出 | 删除/恢复 | 配置与审计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 系统管理员 | 用户、部门、角色、字典、审计和回收范围；不因平台权限自动获得招聘敏感数据 | 查看平台配置和审计；招聘数据需另有业务角色 | 维护用户、组织和字典；不能以管理员身份修改招聘业务记录 | 默认无简历下载权限 | 无 | 可在授权恢复范围内恢复；不能绕过业务数据权限查看内容 | 管理平台配置、查询审计 |
| HR成员 | 全公司招聘数据 | 职位、候选人、面试、评价和历史 | 创建职位、候选人、面试；维护邀约、候选人状态和本人权限范围内评价 | 可下载有权限职位的简历和附件 | 无 | 按权限发起业务软删除；恢复由管理员执行 | 查看与自身权限相关的审计结果 |
| 用人负责人 | 所属部门职位及其候选人、被分配面试和评价 | 查看完整候选人资料及授权范围内评价 | 初筛、面试官指派、面试模板和评价；不能修改 HR 录入的候选人基础资料 | 一期无简历下载权限 | 无 | 无业务删除/恢复权限 | 查看自身操作结果 |
| 面试官 | 被分配面试的职位和候选人；同部门同职位的评价 | 查看授权范围内完整简历和评价 | 只能提交自己的评价，不能修改他人评价 | 一期无简历下载权限 | 无 | 无 | 查看自身面试与评价操作结果 |

- HR成员、用人负责人和面试官的查看、修改和下载均需同时满足角色、数据范围、职位/面试指派和记录状态条件。
- 关闭职位后，已有候选人的授权查看、面试、评价和录用流程不因职位关闭自动失效；新增候选人被阻止。
- 业务数据统一软删除，普通页面不显示软删除记录；管理员恢复必须填写原因并写入审计。
- 简历、附件、评价和权限操作至少审计查看、下载、修改、状态变更、合并、删除、恢复和权限拒绝。

#### G.1 敏感数据生命周期

- 候选人、简历、面试评价和招聘过程记录在招聘结束后按授权范围保留；一期不自动清理。
- 业务删除只改变软删除状态，附件引用同步标记；正式保留期限确认前不物理删除附件。
- 只有管理员可以恢复，恢复必须填写原因并记录恢复前后状态。
- 审计记录追加保存，不提供普通删除或无痕修改入口。
- 用户离职或禁用后不能登录或访问新数据，历史操作人和审计关联保留。
- 一期不开放批量导出；未来开放前需补充审批、字段范围、有效期和审计规则。

#### H. 字典

职位类型、工作地点、招聘角色、面试职级、候选人来源渠道、面试结论、推荐结果、风险项、淘汰原因和候选人放弃原因均为可维护字典。已被业务记录使用的选项只能停用，不能直接删除。

### 7.3 Technology

本 PRD 不规定具体前后端技术栈。实现必须满足以下产品约束：

- 状态变更、权限判断和审计记录需要在服务端生效，不能只依赖前端按钮隐藏。
- 简历附件访问需要进行授权校验并记录下载审计。
- 工作日提醒统一按东八区计算。
- 后续接入飞书 API 时，职位来源字段与 HRM 招聘协作字段需要支持分权维护，不能覆盖已有候选人流程。

### 7.4 Assumptions

| 假设 | 当前处理 | 需要验证 |
| --- | --- | --- |
| HR 愿意把新增职位和候选人迁移到 HRM | 以 HRM 作为后续招聘协作入口 | 试点建档成本和切换阻力 |
| 用人负责人会维护初筛和决策状态 | 设置责任人、工作台和逾期提醒 | 状态责任是否清晰 |
| 面试官愿意填写结构化评价 | 保留文字补充，结构化字段保持少量 | 填写时长和完成率 |
| 公司允许 HRM 保存简历和评价 | 一期避开更敏感的薪酬、合同和档案数据 | 权限和合规评审 |
| 工作台能减少跨表格跟进 | 优先聚合待评价、逾期和长期未推进 | 试点使用行为 |

## 8. Release

### 8.1 第一阶段：基础能力

完成独立账号、首次改密、用户和部门、角色、字典、基础权限、审计框架和软删除能力。

### 8.2 第二阶段：招聘闭环

完成职位建档、职位关闭/恢复、候选人导入、重复提示、候选人阶段、邀约状态、面试模板、面试安排、评价和录用决策。

### 8.3 第三阶段：工作台与试点

完成角色工作台、待评价和逾期面试、长期未推进提醒、权限验收和技术部前端招聘试点。试点通过后再决定是否扩展到其他团队。

### 8.4 后续版本

- 飞书 API 同步职位和职位状态。
- Boss 直聘或其他招聘平台 API 接入。
- 受控批量导出和更完整的数据保留策略。
- 飞书消息或其他通知渠道。
- 绩效管理正式流程。
- 正式效率指标和数据看板。

### 8.5 发布门槛

- 关键业务流程可从职位建档走到录用、淘汰或候选人放弃。
- 角色权限和简历下载权限通过正向及越权用例。
- 候选人阶段不可回退，终止状态不可恢复。
- 重复候选人、关闭职位、公司取消面试和长期未推进提醒规则通过验收。
- 审计记录能够还原关键数据操作，且不能通过普通界面删除。

## 待评审问题

1. 首批试点的正式效率指标和目标值是否在试点开始前补充，指标基线见[指标与试点基线](../../指标与试点基线.md)。
2. 离职员工和候选人数据正式保留期限、主动删除、归档和法律保留依据。
3. 公共验收约定：字段长度、密码复杂度、数值上限、链接长度和附件大小等建议默认值。
