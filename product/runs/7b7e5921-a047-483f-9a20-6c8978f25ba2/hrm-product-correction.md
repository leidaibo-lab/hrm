# HRM 招聘协作首期需求交接稿（人工业务补正）

> 归属 Run：`7b7e5921-a047-483f-9a20-6c8978f25ba2`
>
> 补正原因：本 Run 使用仓库 fixture 模式完成流程门禁，但 fixture 产品角色固定输出“工单标题”样例，不能作为 HRM 业务稿。本文件只依据本 Run 提交的 HRM 原始诉求整理业务交接，不覆盖原始 Workflow 事实，也不宣称经过真实模型质量验收。

## 1. 需求目标

让 HR 与用人负责人在一个地方协作完成候选人初筛和邀约跟进，能够看到当前谁需要处理、处理结果是什么，减少在零散消息中反复确认。

## 2. 本期已确认事实

- 首期范围是候选人初筛与邀约记录。
- 流程止于邀约结果记录，不进入面试安排。
- 使用预置的合成职位和候选人数据。
- 业务角色与人工审批使用本地模拟标签。
- 暂不建设真实账号认证。

以上内容属于原始需求明确给出的基线；其余业务规则不能默认为已批准。

## 3. 建议的最小业务闭环

1. HR 选择一个预置职位，查看候选人列表及候选人基本信息。
2. HR 对候选人记录初筛结果：待处理、通过、淘汰；填写必要的处理说明。
3. 对初筛通过的候选人记录邀约动作：未邀约、已邀约、候选人接受、候选人拒绝、未响应。
4. 用人负责人查看待自己处理的候选人、初筛结果、邀约状态和最近处理人/时间。
5. 所有列表和详情均显示当前状态、最近一次结果和待处理责任标签；不产生面试日程。

## 4. 本期非目标

- 真实账号、单点登录、组织权限和多租户隔离。
- 简历解析、外部招聘网站同步、邮件/短信/微信自动发送。
- 面试排期、面试评价、Offer、入职及候选人转化分析。
- 生产级审计、通知编排和跨系统数据同步。

## 5. 需要在真实产品批准前确认的选择

| 编号 | 待确认选择 | 影响 |
| --- | --- | --- |
| Q1 | 初筛状态是否固定为“待处理/通过/淘汰”，还是允许“待定” | 决定列表筛选、结果必填和是否能进入邀约 |
| Q2 | 只有初筛通过才能记录邀约，还是淘汰/待定也允许补记邀约 | 决定状态机和异常写入校验 |
| Q3 | “当前谁需要处理”按角色标签、具体人标签，还是两者并存 | 决定待办口径及后续接入真实认证的迁移成本 |
| Q4 | 初筛结果、淘汰原因、邀约结果和备注哪些字段必填 | 决定表单阻止提交的条件与验收用例 |
| Q5 | 刷新页面后是否保留本地操作结果，以及是否允许撤销/改写历史记录 | 决定数据持久化、历史展示和错误修正行为 |

建议默认方案：本期采用 Q1 无“待定”、Q2 仅初筛通过可邀约、Q3 角色标签与模拟负责人标签并存、Q4 淘汰原因必填且其它备注选填、Q5 以本地持久化为准并保留最近一次结果，不做不可变审计历史。上述均是建议，不是已批准规则。

## 6. 验收基线（待 Q1–Q5 确认后冻结）

- [ ] 能从预置职位进入候选人列表，并看到候选人、初筛状态、邀约状态、待处理标签和最近处理时间。
- [ ] 初筛提交后，列表和详情显示同一结果；刷新后结果仍符合 Q5 决定。
- [ ] 不满足必填条件时拒绝提交，并明确指出缺少字段；失败提交不改变已有结果。
- [ ] 只有符合 Q2 决定的候选人可以记录邀约，越过前端直接提交也必须被拒绝。
- [ ] 邀约结果更新后，HR 和用人负责人看到同一状态与最近处理信息。
- [ ] 面试安排入口不存在，或明确显示为本期未支持，不产生面试数据。
- [ ] 本地模拟标签可区分 HR 与用人负责人；不得把模拟标签描述为真实认证或安全边界。

## 7. 交接结论

原始诉求已经足以形成范围和非目标，但 Q1–Q5 会改变状态机、字段校验、权限展示或数据保留行为，因此在真实产品批准前仍属于业务阻塞项。本文件可作为后续产品澄清输入，不能替代人工批准。
