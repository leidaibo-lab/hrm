## 2. 业务理解

### 2.1 用户已给出的事实

| 方面 | 已知信息 |
|---|---|
| 建设目标 | 建设公司内部使用的 HRM 系统，同时作为前端团队实践全栈能力的真实项目 |
| 当前问题 | 公司缺少 HRM 系统；招聘信息分散；依靠飞书云盘和零散消息推进；跨角色沟通成本高 |
| 初步模块 | 工作台、招聘管理、绩效管理 |
| 首个业务方向 | 先以招聘作为第一个完整业务闭环 |
| 飞书边界 | 招聘需求申请、审批和职位发布已经在飞书完成，本期希望继续保留，不重复建设审批流 |

| 外部招聘来源 | HR 从 Boss 直聘获取候选人资料和简历 |
| 一期录入方式 | 前期可以人工录入，暂时减少对飞书、Boss 和外部消息的接口依赖 |
| 涉及角色 | HR、用人负责人、面试官、管理员 |
| 招聘动作 | 候选人录入、HR 筛选推荐、用人负责人初筛、HR 记录外部邀约结果、安排多轮面试、提交评价和最终招聘决策 |
| 工作台重点 | 帮助不同角色找到待办，重点关注评价未提交、面试逾期、候选人长期未推进 |
| 试点范围 | 首批可使用技术部前端招聘进行试点 |
| 交付要求 | 最终形成研发、测试、设计无需阅读聊天记录即可使用的中文标准需求文档 |

### 2.2 当前核心问题定义

招聘协作目前缺少一个统一的候选人和招聘过程记录，导致：

1. 候选人资料分散，难以统一查找；
2. HR、用人负责人和面试官之间的责任边界不清晰；
3. 面试评价可能遗漏或逾期；
4. 候选人进入流程后长期没有推进；
5. 招聘状态依靠消息沟通，难以判断当前阶段和下一步动作。

## 3. AI 推荐的一期目标

> 以下为 **AI 建议**，尚未构成用户已确认规则。

### 3.1 一期产品目标

围绕技术部前端招聘试点，建立一个从“已在飞书发布的职位”到“候选人最终招聘决策”的内部协作闭环，使团队能够：

- 统一维护候选人资料和招聘进度；
- 明确每个阶段的责任人；
- 在线完成筛选、邀约记录、面试安排、面试评价和最终决策；
- 让不同角色在工作台看到自己的待办；
- 识别评价逾期、面试逾期和候选人长期未推进等异常。

### 3.2 建议的一期成功判断

建议将效果指标与功能验收分开：

**功能层面：**

- 每个候选人能够关联一个招聘职位并进入明确招聘状态；
- 每个待办能够指向具体候选人、职位和责任人；
- 面试评价提交后能被记录，并解除对应待办；
- 招聘决策后候选人流程能够结束或进入明确的后续状态；
- 无权限角色不能查看或修改不属于其职责范围的数据。

**试点效果层面：**

- 招聘团队不再依赖飞书云盘和零散消息维护候选人主记录；
- 能够通过工作台发现未提交评价、已逾期面试和长期未推进候选人；
- 试点成员能够说清每个候选人的当前阶段、负责人和下一步动作。

具体数值目标、统计周期和“长期未推进”的时间阈值尚未确定，不能直接写入一期验收基线。

## 4. 目标用户与主要场景

### 4.1 首期目标用户

建议首期只覆盖招聘协作直接参与者：

| 用户 | 主要任务 |
|---|---|
| HR | 录入候选人、进行初筛、推荐候选人、记录邀约结果、安排面试、跟进流程、维护招聘信息 |
| 用人负责人 | 查看被推荐候选人、完成初筛、参与最终招聘决策 |
| 面试官 | 查看分配给自己的面试、完成面试评价 |
| 管理员 | 管理账号、角色和基础人员关系，处理人员变更或权限问题 |

### 4.2 关键使用场景

1. HR 将 Boss 直聘中的候选人资料和简历人工录入 HRM。
2. HR 完成候选人初筛，并将合适候选人推荐给对应职位的用人负责人。
3. 用人负责人查看候选人资料并完成初筛结果。
4. HR 记录外部邀约结果，并根据结果继续推进或结束候选人流程。
5. HR 安排一轮或多轮面试，指定面试官和面试时间。
6. 面试官查看自己的待面试事项并提交评价。
7. HR 汇总招聘过程，推动最终招聘决策。
8. 相关角色从工作台查看自己的待办和逾期事项。

## 5. 推荐的一期主流程

> 以下状态和命名为 **AI 建议**，用于形成讨论基线，尚未确认。

### 5.1 流程边界

```text
飞书职位发布完成
        ↓
HR 在 HRM 建立职位协作记录
        ↓
录入候选人
        ↓
HR 初筛
        ↓
用人负责人初筛
        ↓
HR 外部邀约记录
        ↓
安排面试
        ↓
面试官提交评价
        ↓
多轮面试（可选）
        ↓
最终招聘决策
        ↓
录用 / 不录用 / 候选人主动放弃 / 流程终止
```

### 5.2 建议状态流转

| 当前状态 | 触发条件或结果 | 后续状态 |
|---|---|---|
| 待 HR 初筛 | HR 开始处理候选人 | HR 初筛中 |
| HR 初筛中 | HR 通过 | 待用人负责人初筛 |
| HR 初筛中 | HR 不通过 | 已淘汰 |
| 待用人负责人初筛 | 用人负责人通过 | 待邀约 |
| 待用人负责人初筛 | 用人负责人不通过 | 已淘汰 |
| 待邀约 | HR 发起或完成外部邀约记录 | 邀约跟进中 |
| 邀约跟进中 | 候选人接受面试 | 待安排面试 |
| 邀约跟进中 | 候选人拒绝或失联 | 已终止 |
| 待安排面试 | HR 创建面试安排 | 面试中 |
| 面试中 | 当前轮次评价全部完成 | 待面试结论 |
| 面试中 | 评价逾期 | 面试中，产生逾期待办 |
| 待面试结论 | 继续下一轮 | 待安排面试 |
| 待面试结论 | 进入最终决策 | 待最终决策 |
| 待最终决策 | 决策录用 | 已录用 |
| 待最终决策 | 决策不录用 | 已淘汰 |

### 5.3 建议的状态原则

- 一个候选人在同一职位下有一个当前主状态；
- 多轮面试保留轮次记录，不用覆盖历史评价；
- 待办绑定到具体责任人、候选人、职位和业务动作；
- 评价提交后，解除对应评价待办；
- 逾期是待办或提醒属性，不应自动等同于候选人淘汰；
- 候选人终止、不录用、主动放弃等结果应记录原因，并保留历史。

上述原则中，是否允许候选人同时关联多个职位、是否允许退回上一步、是否允许重新激活已终止候选人，仍会改变状态设计和验收，需要后续确认。

## 6. 本期建议范围

### 6.1 建议纳入一期

1. **职位协作记录**
   - 人工建立或录入已在飞书发布的职位；
   - 记录职位名称、部门、用人负责人及招聘协作成员；
   - 不在 HRM 内重新发起审批或对外发布职位。

2. **人员、账号与角色基础能力**
   - 管理 HR、用人负责人、面试官和管理员账号；
   - 配置人员在具体职位上的责任关系；
   - 区分系统角色和具体招聘职位责任。

3. **候选人管理**
   - 人工录入候选人基本资料和简历；
   - 关联招聘职位；
   - 查看候选人当前状态和历史处理记录；
   - 记录候选人来源。

4. **招聘流程协作**
   - HR 初筛；
   - 用人负责人初筛；
   - 外部邀约结果记录；
   - 多轮面试安排；
   - 面试评价；
   - 最终招聘决策。

5. **工作台待办**
   - 按角色展示待处理事项；
   - 展示未提交评价；
   - 展示面试逾期；
   - 展示候选人长期未推进；
   - 待办跳转到具体候选人和动作。

6. **基础历史记录**
   - 记录关键操作人、操作时间、状态变化和处理结果；
   - 保留候选人招聘过程中的关键历史。

### 6.2 本期不纳入

以下为基于当前输入的范围建议：

- 飞书招聘需求申请；
- 飞书招聘审批；
- 飞书职位发布；
- Boss 直聘自动同步或接口接入；
- 飞书消息自动通知；
- 完整员工档案和人事主数据管理；
- 薪资、考勤、假勤等 HRM 能力；
- 绩效管理正式业务闭环；
- 自动简历解析；
- 自动化候选人推荐或 AI 面试评价；
- 面向候选人的外部招聘门户；
- 复杂招聘数据分析和管理层报表。

## 7. 关键假设与高影响待确认项

以下不能被直接写成已确认需求，但会影响后续 PRD、权限、状态和验收。

### 7.1 身份与权限

| 待确认项 | AI 推荐 | 影响 |
|---|---|---|
| 系统角色和职位责任是否分离 | 分离。用户可拥有系统角色，同时在具体职位上承担 HR、用人负责人或面试官责任 | 决定权限模型及同一人兼任多个角色时的行为 |
| HR 是否可查看所有职位和候选人 | 建议首期 HR 可查看其负责范围内的招聘数据；管理员拥有全局管理权限 | 决定候选人敏感信息的访问范围 |
| 面试官能否查看完整简历和薪资等敏感信息 | 建议按最小必要原则限制，仅查看完成面试所需信息 | 决定敏感数据展示和下载规则 |
| 离职、禁用或移除人员后，历史记录如何处理 | 建议保留历史作者和评价，不因账号禁用改写历史 | 决定人员生命周期和审计规则 |

### 7.2 招聘对象关系

| 待确认项 | AI 推荐 | 影响 |
|---|---|---|
| 一个候选人能否关联多个职位 | 建议支持，但每个“候选人—职位”关系独立维护状态 | 决定数据模型、重复候选人处理和流程状态 |
| 一个职位能否有多个用人负责人 | 建议支持一名主负责人，可配置协作负责人 | 决定初筛权限及待办归属 |
| 一个面试是否允许多个面试官 | 建议支持多个面试官，每人独立提交评价 | 决定评价完成条件和逾期规则 |
| 是否允许候选人重复录入 | 建议按联系方式或人工确认提示潜在重复，不一期自动合并 | 决定数据冲突处理和历史保留 |

### 7.3 流程与状态

| 待确认项 | AI 推荐 | 影响 |
|---|---|---|
| 是否允许退回上一阶段 | 建议允许在有限条件下退回，并要求记录原因 | 影响状态图、操作权限和历史 |
| 是否允许跳过邀约直接安排面试 | 建议不允许，除非记录外部邀约结果或明确线下来源 | 影响流程完整性和验收 |
| 多轮面试的完成条件 | 建议当前轮次所有已分配面试官提交评价后，才可进入面试结论 | 影响待办解除、逾期和下一轮激活 |
| “长期未推进”的阈值 | 建议一期配置为业务参数，默认值需产品负责人确认 | 影响工作台展示和成功指标 |
| 面试逾期的计算口径 | 建议按面试计划结束时间且评价未提交判断 | 影响逾期提醒和测试边界 |
| 最终招聘决策角色 | 建议由用人负责人作业务决策，HR 负责记录和推进 | 影响权限及最终状态转换 |

### 7.4 敏感数据治理

需要确认：

- 简历、联系方式、薪资期望等字段分别属于何种敏感等级；
- 谁可以查看、编辑、下载或导出；
- 是否需要操作日志；
- 候选人数据保存多久；
- 是否允许删除，删除后是否保留脱敏历史；
- 面试评价是否允许被他人修改，修改是否需要保留版本。

这些问题会直接影响一期能否安全用于真实招聘试点。

## 8. 推荐推进顺序

建议按业务依赖分轮推进，而不是先分别设计工作台、招聘管理和绩效管理。

### 第 1 轮：确定招聘对象与责任关系

先确定：

1. 职位、候选人、面试、评价之间的关系；
2. 系统角色与职位责任的区别；
3. HR、用人负责人、面试官和管理员的查看、编辑、提交权限；
4. 候选人是否可以关联多个职位；
5. 一职位是否可以配置多个负责人和面试官。

**原因：**这些规则决定数据结构、权限边界和后续所有页面。

### 第 2 轮：收敛招聘主流程与状态

确定：

1. 候选人状态；
2. 每个状态的进入条件和退出条件；
3. 退回、终止、放弃、淘汰和重新激活；
4. 多轮面试完成条件；
5. 最终招聘决策责任；
6. 异常和失败时是否保留输入。

**原因：**没有稳定的状态模型，工作台待办和验收无法准确设计。

### 第 3 轮：定义字段、页面和操作

按流程补齐：

1. 职位协作记录；
2. 候选人录入和详情；
3. 初筛、邀约、面试和评价；
4. 最终决策；
5. 工作台待办；
6. 敏感信息展示与下载。

### 第 4 轮：定义异常、数据治理和指标

补齐：

- 重复候选人；
- 人员禁用或责任变更；
- 面试改期、取消和逾期；
- 评价漏填；
- 并发修改；
- 敏感数据访问；
- 候选人长期未推进；
- 试点成功指标。

### 第 5 轮：形成正式双文档

在关键业务选择完成后，再编写：

- 产品项目总览；
- 招聘模块 PRD；
- 用户故事与研发任务；
- 验收场景与测试覆盖；
- 内部执行记录和决策记录。

后续应优先确认或审阅以下 AI 推荐方案：

1. 系统角色与职位责任分离；
