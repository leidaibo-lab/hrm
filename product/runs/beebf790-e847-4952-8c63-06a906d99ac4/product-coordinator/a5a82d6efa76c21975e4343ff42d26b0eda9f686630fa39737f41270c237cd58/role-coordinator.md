# 本轮统筹说明（招聘闭环试点）

## 1. 当前阶段判断

当前处于**产品发现/需求澄清的第 0 轮**，尚不能进入完整 PRD 编写或研发排期。

**依据：**
- 已明确业务痛点、试点部门和大致协作链路；
- 尚未确认角色授权模型、招聘主流程状态及关键节点的决策权；
- `intake` 显示尚未开始人工确认轮次，当前没有历史答复；
- 当前材料中没有返工反馈或既有评审结论。

因此，本轮只形成统筹与首轮澄清议题；不把推荐方案写成已确认需求，也不提前产出完整 PRD。

---

## 2. 已确认的业务理解与边界

### 2.1 项目总目标（输入事实）

建设公司内部 HRM，兼顾两类目标：

1. **业务目标**：降低招聘信息分散、候选人协作依赖飞书云盘/零散消息、跨角色沟通成本高的问题。
2. **实践目标**：以真实内部项目实践前端团队的全栈能力，并为后续企业级 HRM 模块扩展打基础。

### 2.2 首个业务闭环（输入事实）

首期优先做**招聘管理**，试点为**技术部前端招聘**。系统从职位发布后的内部招聘协作开始承接：

> HR 从 Boss 直聘等外部渠道获得候选人资料/简历 → 手工录入 HRM → HR 筛选推荐 → 用人负责人初筛 → HR 记录外部邀约结果 → 安排多轮面试 → 面试官提交评价 → 最终招聘决策。

### 2.3 已确认边界

| 类别 | 已确认内容 |
|---|---|
| 上游流程 | 招聘需求申请、审批、职位发布继续在飞书完成。 |
| 本系统起点 | 职位发布后的内部招聘协作。 |
| 外部集成 | 前期可人工录入；暂不依赖飞书、Boss 直聘接口及外部消息能力。 |
| 核心使用者 | HR、用人负责人、面试官、管理员。 |
| 首期待办重点 | 评价未提交、面试逾期、候选人长期未推进。 |
| 后续方向 | 工作台、招聘、绩效管理均是规划方向；招聘先形成完整闭环。 |

### 2.4 目前不应视为首期已确认范围的事项

- 飞书审批/职位发布的迁移或重建；
- Boss 直聘、飞书或外部消息渠道的接口打通；
- 绩效管理具体能力；
- 企业级“标准模块”的具体清单、阶段、优先级；
- 自动提醒渠道、自动化催办和升级规则；
- 正式可量化成功指标、上线门槛及数据基线。

## 3. 请求分诊与本轮重点

当前不是来自多个用户/渠道的批量需求池，而是一组项目初始诉求；不具备按频次、收入或用户覆盖量评分的材料，**不编造 RICE/价值评分**。按“是否决定首期边界、是否阻塞主流程”的依赖关系分诊如下。

| 优先级 | 需求主题 | 当前处理结论 | 优先级依据 |
|---|---|---|---|
| P0 | 招聘闭环的起止范围、主状态与最终决策 | 首轮澄清 | 决定对象模型、页面、权限、待办和验收基线。 |
| P0 | 账号、组织角色与职位级责任分工 | 首轮澄清 | 涉及候选人简历及评价等敏感数据；不先定则无法定义可见范围和操作权。 |
| P0 | 试点岗位/职位来源及如何进入 HRM | 首轮澄清 | 飞书仍承担发布，但 HRM 如何取得“可协作职位”尚不明确，主流程无法启动。 |
| P1 | 候选人字段、简历治理、重复候选人和敏感数据规则 | 第二轮 | 依赖角色及可见范围的确认；直接影响数据模型与合规风险。 |
| P1 | 面试轮次、邀约记录、评价、逾期与未推进处理 | 第二轮 | 依赖状态机、时限口径和责任人确认。 |
| P1 | 工作台待办的分类、排序、提醒/升级 | 第二轮 | 必须由主流程事件和责任归属驱动，不宜先做孤立工作台。 |
| P2 | 指标、看板、试点验收阈值 | 第三轮 | 需在流程、状态、事件和数据采集范围确定后定义。 |
| P2 | 绩效管理、外部集成、HRM 其他标准模块 | 后续规划 | 不应破坏招聘试点的可交付性；保留扩展边界，不纳入当前闭环。 |

**取舍原则：** 先解决“职位如何进入—谁能处理—候选人如何流转—何时结束”的闭环，再做字段细化、待办效率和扩展模块。这样可以避免先做页面或工作台，却没有稳定的业务事件与责任对象可承接。

## 4. 推荐的固定推进顺序

不创建下级 Agent，也不跳过人工确认关口；建议沿固定角色顺序推进：

1. **总产品统筹（当前）**  
   固化项目目标、范围、依赖和本轮关键待决项；确定本轮只讨论 P0。
2. **需求梳理角色**  
   在获得人工回答后，展开：职位承接方式、角色/职位级责任、候选人主流程及状态决策；明确规则、异常和业务词汇。
3. **产品闭环角色**  
   仅在上述 P0 决策确认后，补齐状态转换、待办触发、权限边界、敏感数据治理、字段、异常路径和可验证的闭环条件。
4. **产品写作角色**  
   汇总已确认规则与仍阻塞的待决项，输出完整的项目总览、招聘模块 PRD 和验收配套；不把推荐或未答问题写为已确认规则。
5. **人工确认关口**  
   对范围、关键流程、权限、数据可见性、验收标准进行人工确认后，再作为研发测试设计的正式基线。

## 5. 首轮需人工确认的问题（仅 P0）

以下问题按影响范围排序。当前没有交互式确认工具，均保留为**待人工确认**，不默认采用推荐项。

### Q1：首期“可协作职位”如何从飞书进入 HRM？

**背景：** 飞书继续负责需求、审批和职位发布，但 HRM 需要一个已发布职位作为候选人归属、负责人分配和流程统计的载体。

| 选项 | 说明 | 影响 |
|---|---|---|
| A（推荐） | 管理员或 HR 在 HRM 手工创建“协作职位”，录入飞书职位链接/编号、职位名称、部门、用人负责人和状态。 | 首期无需集成；会形成一次轻量重复录入；后续可用飞书同步替换。 |
| B | HRM 只记录职位名称，不保留飞书职位引用。 | 实现较轻，但跨系统追溯和后续集成基础较弱。 |
| C | 首期即接入飞书自动同步。 | 减少录入但显著扩大集成、权限、异常同步及验收范围，与“前期减少外部依赖”存在张力。 |

**请确认：** 选 A / B / C，或给出其他规则。  
**若选 A，还需确认：** HRM 内的协作职位由谁创建、谁可以关闭/归档。

---

### Q2：一个人在不同招聘职位上的身份和决策权如何确定？

**背景：** “HR、用人负责人、面试官、管理员”是角色类别，但同一员工可能同时担任多个角色，且权限应随具体职位变化。

| 选项 | 说明 | 影响 |
|---|---|---|
| A（推荐） | “系统角色 + 职位级分工”：管理员维护基础账号/角色；每个协作职位单独指定 HR、用人负责人和面试官。系统权限取账号角色与该职位职责的交集。 | 最符合多岗位协作；可避免无关人员看到候选人信息；规则较多，需后续明确权限矩阵。 |
| B | 仅采用全局角色：所有 HR/负责人/面试官按全局角色获得同类职位权限。 | 实现简单，但候选人和评价的最小授权较弱。 |
| C | 以管理员逐人逐职位配置权限为主。 | 最灵活，但配置成本高，易产生遗漏和权限不一致。 |

**请确认：** 选 A /B /C。  
**若选 A，还需同时确认：**
- 用人负责人能否自行增减本职位面试官；
- 面试官是否只看自己被安排的面试及必要候选人资料；
- HR 是否可查看所有职位，还是仅查看被分配职位。

---

### Q3：候选人的首期主流程以哪个业务节点为准？最终由谁作出决策？

**背景：** 用户已提出关键动作，但尚未定义状态、回退/终止规则、决策主体及终点，工作台的“逾期”“长期未推进”也无从计算。

| 选项 | 说明 | 影响 |
|---|---|---|
| A（推荐，作为待确认草案） | 候选人进入：`已录入 → HR 筛选中 → 待负责人初筛 → 待邀约/邀约处理中 → 面试进行中 → 待汇总决策 → 已录用 / 未录用 / 主动放弃`。HR负责流程推进及外部邀约结果记录；用人负责人在面试结束后提交业务录用建议；由指定终审角色落最终结果。 | 覆盖已知流程，适合待办驱动；仍须明确每个节点责任人、时限和终审角色。 |
| B | 用人负责人初筛后直接决定录用/淘汰，面试仅作辅助记录。 | 流程较短，但与多轮面试、面评提交的闭环关系需重新定义。 |
| C | HR 作为唯一最终决策录入人，用人负责人和面试官仅提供意见。 | 便于数据归口，但需要确认是否符合公司实际授权。 |

**请确认：**
1. 是否以 A 作为首期状态主干，哪些状态需增删或改名；  
2. 谁拥有“最终录用/未录用”落库权：HR、用人负责人、两者之一经确认后执行，还是其他角色；  
3. “候选人长期未推进”的起算节点与阈值（例如按状态停留自然日/工作日）；目前没有阈值，不应自行设定。
