# 内部 HRM 招聘协作系统
## 项目总览、招聘管理与招聘待办工作台需求稿

**文档状态：** 写作稿，尚未形成完整需求基线  
**适用对象：** 产品、研发、测试、设计  
**版本范围：** 首期招聘协作与招聘待办工作台  
**重要说明：** 已确认规则可作为本稿的需求依据；建议和未决项不构成已批准行为。完整招聘链路、关键权限和试点最低验收门槛仍有阻塞。

## 1. 项目总览

### 1.1 背景与目标

公司目前缺少 HRM 系统，招聘资料分散在招聘平台、飞书云盘和零散消息中，跨角色沟通和推进成本较高。团队希望借真实业务项目实践全栈能力，同时先解决招聘协作问题。

首期建设内部 HRM 招聘协作系统：飞书继续承担招聘申请、审批和职位发布；HRM 从职位发布后承接招聘信息与过程协作，覆盖招聘推进至候选人实际到岗或确认未到岗，并提供面向不同角色的招聘待办工作台。

### 1.2 目标用户与场景

- **HR：** 录入候选人资料、筛选推荐、记录外部邀约、安排面试并跟进招聘结果。
- **用人负责人：** 初筛候选人，并作出最终招聘决定。
- **面试官：** 按指定轮次参与面试并提交评价。
- **管理员：** 系统涉及此角色，但其对敏感招聘资料的访问权限尚未确认。

首批试点对象为技术部前端高级开发招聘，涉及 4 位 HR，预期筛选数百位候选人；面试官按业务线及轮次安排。用户希望于 2026 年 11 月 15 日开始使用，但最低试用结果尚未明确；该日期是期望，不是已评估的工程交付承诺。

### 1.3 价值主张

**HR：** 当招聘资料和推进状态分散、需要跨角色协调时，HR 需要在一个内部工作区中记录候选人资料、招聘过程和跟进事项；相比继续依赖云盘与零散消息，系统应让资料和责任更集中、进展更易跟踪。候选人和过程字段、待办触发规则及实际节省效果仍待确定。

**用人负责人和面试官：** 当需要筛选候选人或完成某轮评价时，他们需要看到自己参与范围内的招聘信息并完成相应动作；HRM 承接职位发布后的内部协作，飞书申请、审批和职位发布仍保留。

### 1.4 成功衡量

当前没有确认的指标基线、目标值或试点最低通过门槛。建议后续以招聘资料集中度、跨角色事项逾期情况、候选人停滞情况及实际到岗记录完整性为候选衡量方向；这些仅为建议，不能据此判定上线或试点通过。

## 2. 范围与非目标

### 2.1 首期范围

- 职位发布后的内部招聘协作。
- 人工录入候选人资料和招聘过程；集中管理简历与招聘资料。
- 按职位及招聘参与关系分配 HR、用人负责人和面试官职责。
- 提供招聘待办工作台，重点关注评价未提交、面试逾期、候选人长期未推进。
- 跟踪候选人是否实际到岗或未到岗；实际到岗才计为已使用名额，到岗前单列待入职人数。

### 2.2 明确不纳入首期

- 替代飞书的招聘申请、审批和职位发布流程。
- 绩效管理，已延后。
- 依赖飞书、Boss 直聘接口或外部消息服务实现自动同步、通知或自动化；首期允许人工录入。
- 未经确认的自动招满、自动停招、候选人自动合并或其他自动流程。

## 3. 招聘管理模块 PRD

### 3.1 已确认业务规则

| 主题 | 需求基线 | 依据 |
|---|---|---|
| 招聘边界 | HRM 从职位发布后的内部协作开始；飞书继续处理申请、审批和职位发布 | 原始 brief；人工确认的首期范围 |
| 招聘终点 | 招聘过程持续至候选人实际到岗或未到岗，包含录用沟通；不办理员工入职手续 | 第二轮人工确认 `endpoint_followup_boundary=through_actual_arrival`，取代首轮“最终决策”终点及旧建议 |
| 名额统计 | 只有实际到岗才计为职位已使用名额；到岗前单列待入职人数 | 第二轮人工确认 `headcount_consumption=actual_arrival`；不得改用“接受录用即占用” |
| 职位职责 | 每职位一名主责 HR 和一名用人负责人；面试官按轮次指定 | 人工确认的角色规则 |
| 招聘动作 | HR 推进；负责人初筛并作最终招聘决定；面试官提交评价 | 人工确认的职责分工 |
| HR 协作 | HR 可共享查看招聘资料；其他 HR 需要明确转交或授权后才能代办。共享查看不等于共同修改 | 第二轮人工确认 `hr_collaboration_authority=owner_with_handover` |
| 参与访问 | 负责人和面试官按参与范围访问招聘资料 | 人工确认的访问边界；细粒度字段范围待定 |

### 3.2 核心流程概述

下列步骤表达已确认职责及业务目标，不代表所有状态转换、前置条件及异常行为均已确定：

1. 职位在飞书完成发布后，由内部流程承接招聘协作。
2. HR 录入候选人资料并推进招聘。
3. HR 筛选推荐，负责人进行初筛。
4. HR 记录对外邀约结果，并安排一轮或多轮面试。
5. 面试官提交对应轮次评价。
6. 负责人作最终招聘决定；HR 继续记录录用沟通并跟进实际到岗或未到岗结果。
7. 只有实际到岗才计入已使用名额；到岗前人数需单独体现为待入职人数。

候选人与应聘记录如何关联、每个步骤如何进入或退出、跳过或回退规则、未到岗的终结处理均未确认，因此本流程不能直接作为完整状态机或无条件验收基线。

### 3.3 角色和权限边界

| 角色 | 已确认职责或权限 | 尚未确定 |
|---|---|---|
| 主责 HR | 负责该职位招聘推进；HR 共享查看范围内可查看资料 | 哪些写入需要何种授权；主责变更后待办如何处理 |
| 其他 HR | 可共享查看；须有明确转交或授权后才能代办 | 转交与临时代办的发起、批准、范围、期限、撤销及接管规则 |
| 用人负责人 | 按参与范围访问；负责候选人初筛及最终招聘决定 | 参与关系配置、可见字段、决定条件及越权操作反馈 |
| 面试官 | 按参与范围访问；提交指定轮次评价 | 跨轮次评价可见性、评价修改规则及资料下载权限 |
| 管理员 | 系统包含此角色 | 管理员是否可查看敏感招聘资料及相关审计规则 |

权限要求应覆盖实际写入入口，不能只依赖页面隐藏来阻止越权。具体拒绝反馈、审计记录及各类敏感字段权限尚待业务确认。

## 4. 招聘待办工作台 PRD

工作台的已确认目标是帮助不同角色找到自己的招聘待办，重点覆盖以下三类问题：

| 待办方向 | 输入目标 | 尚待确定的业务规则 |
|---|---|---|
| 评价未提交 | 找出需要提交面试评价的事项 | 何时生成、起算事件、责任人、逾期阈值、提交后如何消除 |
| 面试逾期 | 找出超过约定时间仍未完成的面试事项 | 逾期定义、改期或取消后的处理、提醒对象 |
| 候选人长期未推进 | 找出长时间没有推进的招聘记录 | “推进”的定义、起算时间、阈值、重置规则及退出后处理 |

系统必须在最终规则确认后，才能用确定的事件和边界验收这三类待办。当前不能据此推断具体提醒时间、自动催办方式、刷新时机、去重逻辑或逾期阈值。转交、授权、改期、候选人退出或职位关闭时，待办归属与清除方式也未确定。

## 5. 验收配套

下表保留闭环材料中的 A01–A12 与 T01–T12 编号。它们是验收目标及测试设计，不代表测试已运行或结果已通过。标为“待定”的预期不得交付为可执行验收标准。

| 编号 | 验收目标 | 当前可确认的判定边界 |
|---|---|---|
| A01 / T01 | 人工录入及资料复用 | 验证资料可查询及 HR 共享查看；必填字段、文件限制、重复处理未定 |
| A02 / T02 | 招聘链路职责接力 | 必须符合已确认分工并可继续跟踪到实际到岗；初筛选项、轮次规则、评价齐备要求待定 |
| A03 / T03 | 到岗与名额计数 | 录用决定、薪资沟通或填写预计到岗日期本身不得使已使用人数增加；实际到岗计入已使用人数 |
| A04 / T04 | 待入职达到计划数时的边界 | 不得将待入职人数等同已使用人数；是否继续邀约、面试或录用待定 |
| A05 / T05 | HR 共享查看与写入权限分离 | 未获转交或授权的其他 HR 不得因共享查看而获得代办权限；授权细节待定 |
| A06 / T06 | 转交、代办和撤销 | 需检查责任、操作权和待办归属是否一致；执行规则待定 |
| A07 / T07 | 按参与范围访问 | 明确未参与的负责人或面试官不应获得相关招聘资料；细分范围和管理员权限待定 |
| A08 / T08 | 拒绝、撤回、缺席、取消及回退 | 必须先确定终结、恢复、评价留存及待办处理规则；当前无完整判定预期 |
| A09 / T09 | 三类工作台事项 | 需逐项确认生成、责任人、去重、重置、消除和刷新规则后测试 |
| A10 / T10 | 到岗重复提交或更正 | 有效到岗事实的计数口径已确认；重复提交防重、更正权限和历史记录要求待定 |
| A11 / T11 | 保存失败、重试和并发修改 | 需明确失败后保存的数据、关联状态与待办结果、冲突处理及重试规则 |
| A12 / T12 | 职位暂停或关闭 | 需明确在途候选人、待入职、待办和后续登记的处理方式 |

### 5.1 适用的可观察判定

- **名额口径：** 对同一职位的一条应聘记录，在最终招聘决定后但尚未实际到岗时，已使用人数不因该决定自动增加；登记实际到岗后，该记录计入已使用人数。待入职人数应与已使用人数分开。待入职的起算及离开条件仍待确认。
- **HR 权限边界：** 对没有明确转交或授权的 HR，查看共享资料不得被解释为获准代办。具体需受控的写入动作及拒绝后的系统行为，需在权限规则补齐后逐项验收。
- **参与范围：** 对明确未参与某职位或候选人的负责人或面试官，不能仅靠隐藏列表通过验收；还需核实直接访问及资料入口不泄露业务资料。管理员和敏感字段例外规则待确认。
- **完整链路：** 招聘跟进包含录用沟通，并以实际到岗或未到岗结果为范围边界；由于退出和恢复规则尚未定义，端到端链路目前不具备完整验收条件。

### 6.2 已确认决策与历史建议区分

- 已确认：首期招聘协作及招聘待办工作台；绩效延后；申请、审批、职位发布保留在飞书；人工录入；招聘追踪至实际到岗或未到岗；只有实际到岗才计为已使用名额；HR 主责推进、共享查看与代办权限分离。
